### 1) File: safe-eval.ts
- Location: safe-eval.ts
- Current code:
```ts
import vm from "vm";

export function safeEval(input: string, context: any = {}) {
  const sandbox = { ...context };
  return vm.runInNewContext(input, sandbox);
}
```

#### Vulnerability (Exact mechanism)
- `vm.runInNewContext` executes arbitrary JavaScript (host runtime).
- The sandbox receives host objects (e.g., `console` from main context). Functions on those objects have a `.constructor` that points to the Function constructor. An attacker can invoke `console.log.constructor('...')()` or other patterns to get a Function that runs in the host context and access `require`, `process`, or `child_process`.
- Example primitive exploit:
  - Code executed by the sandbox:
    ```
    console.log.constructor('return require("child_process")')()
      .execSync('cat /etc/passwd')
    ```
  - That would return the `child_process` module and call `execSync`.

#### How an attacker triggers it (plausible steps)
- Attacker sends a base64 payload encoded string to `runUserInput` (via `index.ts` or an endpoint).
- The payload decodes to JS code that uses `console.log.constructor` to obtain Function and `require()`.
- They then call `require('child_process')` and exec any commands (read files, run binaries, pivot, etc).

#### Realistic Impact
- Full Remote Code Execution (RCE) under the application's runtime user account.
- Arbitrary file read/write via `fs`.
- Network access via `net/http`, data exfiltration.
- Potential lateral movement and privilege escalation if the runtime user has extra privileges.

#### Corrected Safe Redesign (Actionable)
- *Short version:* Don’t run untrusted JS in Node.js directly. If required, use a secure, well-configured sandbox and do not pass host function references into sandbox. Better: avoid code eval entirely and use domain-specific interpreters.
- *Key changes*:
  - Remove `safeEval` or make it not execute arbitrary JS from untrusted sources.
  - If you *must* allow expressions, use one of:
    - A safe expression evaluator or a domain-specific parser (math expr; no function creation).
    - A hardened sandbox using `vm2` with strict options and disabled `require`, and **do not** pass host functions into the sandbox.
    - Offload execution to a separate process or microservice with strict OS-level constraints (non-privileged user, container, seccomp profile).
  - Enforce AST-level filtering: parse with `acorn`/`esprima` to reject `Function`, `CallExpression` of `Function`, `NewExpression`, `eval`, `require`, `process`, `constructor`, etc.
  - Enforce HMAC signature checks to ensure the code originated from a trusted source.
  - Use timeouts and memory constraints.
  - Return safe, sanitized results only (never pass the raw module back).
  - Add logging/monitoring and fail open/close policies.

#### Example Safe Implementation (simple express approach)
- If you want to evaluate *bespoke arithmetic or expressions*, prefer this safe setup:
  - Use an expression-only evaluator instead of JS:
    - `expr-eval` or `mathjs` or similar; these evaluate safe expressions without allowing arbitrary calls or constructors.

Example replacement (toy demonstration: arithmetic evaluator):
```ts
// safe-eval.ts (safe expression evaluator approach)
import { Parser } from "expr-eval";

export function evaluateExpression(expression: string, context: Record<string, number> = {}) {
  // Validate expression length
  if (expression.length > 2048) {
    throw new Error("Expression too long");
  }
  // Disallow suspicious tokens (sanity only - use AST checks)
  if (/require|process|constructor|Function|eval|global|this/.test(expression)) {
    throw new Error("Unsafe tokens present");
  }
  const parser = new Parser();
  const expr = parser.parse(expression);
  // Allowed variable map only
  return expr.evaluate(context);
}
```

Example `vm2`-based approach (if you *must* run some JS):
```ts
// safe-eval.ts (using vm2 with restrictions)
import { VM } from "vm2";

export function safeEval(input: string, context: any = {}) {
  // Basic token blacklist - not sufficient by itself; use AST checking.
  const blacklist = /require|process|constructor|Function|eval|global|this/;
  if (blacklist.test(input)) {
    throw new Error("Unsafe code detected");
  }
```

Important notes:
- `vm2` must still be configured carefully; keep update dependencies and peer review.
- Do not use host-provided function objects (like `console`) as they can expose constructors. Instead, provide only safe primitives or a logging function that forwards to a safe logger:

```ts
const sandboxLogger = { log: (msg: string) => { /* write to server-safe logging pipeline */ } };
const vm = new VM({ sandbox: { console: sandboxLogger } });
```

- Ultimately prefer microservice-level separation (separate process / container and run as a non-privileged user).

### 2) File: `utils/decodePayload.ts`
- Location: `utils/decodePayload.ts`
- Current code:
```ts
export function decodePayload(str: string) {
  // Obfuscated: base64 → reversed string → JS code
  const reversed = Buffer.from(str, "base64").toString().split("").reverse().join("");
  return reversed;
}
```

#### Vulnerability (Exact mechanism)
- The function decodes base64 and returns an arbitrary string (potentially executable code).
- The encoded payload hides the attacker’s intention and allows bypassing content-based protections (signature checks, pattern detection).
- No validation or structural checks on the payload (e.g., is it JSON, command, expression?).

#### How an attacker triggers it
- An attacker encodes malicious JS in base64, reversed intentionally to bypass filters.
- Calls `runUserInput` with the payload.

#### Impact
- If `safeEval` runs decoded content, attacker gains RCE and full control of operations on the node runtime.

#### Corrected Safe Redesign (Actionable)
- Do not treat arbitrary strings as code. Instead:
  - Define a strict payload schema (JSON with `type`, `version`, `payload`).
  - Use JSON rather than raw code. For example:
    ```json
    {"type":"math-expression","payload":"1+2*3","nonce":"...", "signature":"..."}
    ```
  - Validate schema and content type; use an HMAC signature to ensure the payload came from a trusted sender.
  - Disallow code types that require execution unless explicitly verified and signed.
- Example decode and validation:
```ts
import crypto from "crypto";

const HMAC_SECRET = process.env.HMAC_SECRET || "supersecret";

export function decodePayloadSafe(str: string) {
  const buf = Buffer.from(str, "base64");
  const reversed = buf.toString().split("").reverse().join("");
  let obj;
  try {
    obj = JSON.parse(reversed);
  } catch (err) {
    throw new Error("Payload not JSON");
  }
  // Check only allowed types
  const allowedTypes = new Set(["math-expression", "command-v1"]);
  if (!allowedTypes.has(obj.type)) {
    throw new Error("Disallowed payload type");
  }
  // Verify signature if present
  if (!verifySignature(obj)) {
    throw new Error("Invalid signature");
  }
  return obj;
}

function verifySignature(obj) {
  if (!obj.signature || !obj.nonce) return false;
  const payload = Buffer.from(JSON.stringify({ type: obj.type, payload: obj.payload, nonce: obj.nonce })).toString();
  const hmac = crypto.createHmac("sha256", HMAC_SECRET).update(payload).digest("hex");
  return hmac === obj.signature;
}
```
- Reject any payload containing suspicious tokens (require, process, constructor). Use additional AST parse if needed.
- Logging of suspicious payloads.

## Additional Design and Hardening Recommendations

1) Remove all host object references from the sandbox. Do not pass stream objects or functions from the host (e.g., `console`) into the sandbox. Instead, pass controlled, primitive values or proxy objects with a *no-*constructor signature.

2) Add AST enforced policies:
- Use `acorn` or `esprima` to parse incoming code and reject or rewrite it if any disallowed nodes exist:
  - Disallow `NewExpression`, `Function`, `ArrowFunctionExpression`, `CallExpression` of `Function`, `Identifier` of `require`/`process`.
  - Allow only whitelisted node types (Literal, BinaryExpression, UnaryExpression, ConditionalExpression, MemberExpressions that follow allowed patterns, etc).

3) Enforce invocation restrictions:
- Use HMAC signatures on payloads and only accept payloads that are signed by a trusted entity (to ensure code comes from authorized source).
- Additionally, include a `nonce`/timestamp and enforce TTL to prevent replay.

4) Resource control and OS-level isolation:
- Run any dynamic code evaluation inside a separate process/VM/container with:
  - Non-root account
  - No network access unless explicitly allowed
  - Limited CPU/time limits
  - Filesystem access only to a readonly, specific directory
  - Logging of execution for audit

5) Logging, alerting and monitoring:
- Deny and log attempts to use suspicious properties: `Function`, `constructor`, `require`, `process`.
- Consider integrating a threat detection rule to flag suspicious inbound payloads.

6) Remove or adapt any demo code which runs arbitrary payloads in index.ts. Monkey patch or gating functions for developers only.

7) Secure the deployment environment:
- Do not run Node/JS processes as admin/root.
- Use containerization with enforced boundaries for apps that execute dynamic code.
