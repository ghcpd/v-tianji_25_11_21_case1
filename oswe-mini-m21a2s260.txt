Summary
- I inspected your project and found multiple high-severity issues that enable remote arbitrary code execution (RCE), privilege escalation, and DoS. The root cause is unsafe dynamic evaluation of untrusted input with insufficient sandboxing and no resource limits.
- Below I list each issue with the exploitation mechanism, a realistic trigger, impact, and a precise, actionable remediation.

Vulnerability 1 — Arbitrary code execution via vm.runInNewContext
- Code location: safe-eval.ts, called from userInput.ts and index.ts.
- Mechanism: The app decodes a Base64 payload to produce JS source, then executes it with Node’s `vm.runInNewContext`. The code is untrusted, and `vm.runInNewContext` by itself is not a safe sandbox. The code can use the Function constructor or prototype/constructor-chains to escape the sandbox and reach Node internals (process, require, etc.).
- Realistic exploit:
  - Attacker sends a Base64 value that decodes to JS like:
    this.constructor.constructor('return process')().mainModule.require('child_process').exec('rm -rf /')
  - The app decodes and runs it; the attacker gets shell execution.
- Impact: Full RCE as the Node process user — read/write files, run shell commands, exfiltrate secrets, delete data, pivot into network.
- Fix (precise):
  1. Remove dynamic evaluation of arbitrary strings entirely. Replace any “eval-like” behavior with a restricted DSL or trusted, signed templates.
  2. If evaluation is required, never run it in the main process — execute in a separate OS-isolated process (unprivileged user or container) and use strict IPC. Do not use Node `vm` for serious untrusted code execution.
  3. If you must use a JS evaluator, use a dedicated native module with strong isolation: the recommended one is isolated-vm (https://github.com/laverdet/isolated-vm) which gives true V8 isolates with memory limits and timeouts. Example:

    // Suggested safe-eval (use inside a worker process)
    import ivm from 'isolated-vm';

    export async function safeEvalIsolated(code: string, timeout = 100) {
      const isolate = new ivm.Isolate({ memoryLimit: 32 }); // MB
      const context = await isolate.createContext();
      const jail = context.global;
      await jail.set('log', (...args: any[]) => {}); // provide safe logging
      // extremely restrictive: no access to require/process
      const script = await isolate.compileScript(code);
      return await script.run(context, { timeout });
    }

  4. Authentication: only run code that is signed or comes from a trusted end-point (HMAC/JWT). Do not accept arbitrary uploaded code from users.

Vulnerability 2 — Insecure “sandboxing”: console injection and prototype leaks
- Code location: userInput.ts and safe-eval.ts.
- Mechanism: The context object passed to the VM only adds `console`, but an attacker can still obtain the global Function via .constructor or prototype chains, then reach `process` or `require`. Passing `console` is not enough to prevent escapes.
- Exploit trigger: Same as above — attacker uses constructor or prototype chain in evaluated code to reach Node internals.
- Impact: Same as Vulnerability 1.
- Fix (precise):
  - Don’t rely on `vm.runInNewContext` alone. If you must use `vm`, do not create a context with object prototypes that allow Function constructors — use third-party secure sandboxes such as SES (https://github.com/endojs/endo/tree/main/packages/ses) or isolated-vm. Also ensure you freeze prototypes and remove dangerous built-ins before code runs — however, this pattern is risky and easy to get wrong. Prefer process-level isolation.

Vulnerability 3 — No CPU / Memory limits and no timeout (DoS)
- Code locations: safe-eval.ts and decodePayload.ts.
- Mechanism: `vm.runInNewContext` is called without `timeout` or memory limits. Untrusted code could run infinite loops or allocate huge buffers.
- Exploit trigger:
  - Payload: while (true) {} or Buffer.alloc(1 << 30)
  - Impact: Worker hangs or the main process exhausts memory — DoS for the service.
- Fix (precise):
  - Use a hardened runtime with enforced time and memory limits (e.g. isolated-vm with memory and timeout). If using `vm.Script.runInNewContext`, pass { timeout: ms } (Node 10+) and also run in a separate child process with memory limits enforced by OS/container.
  - Validate/limit the decoded payload size in `decodePayload` (max bytes) and the number of characters.

Vulnerability 4 — Unvalidated Base64 input and huge payloads
- Code location: decodePayload.ts.
- Mechanism: decodePayload blindly base64→string and reverses it without verifying length or character set.
- Realistic exploit: Extremely long base64 string or payload causing excessive memory usage and crash.
- Impact: Denial-of-service (memory exhaustion), crashes.
- Fix (precise):
  - Enforce maximum allowed base64 length and decoded length; reject if larger.
  - Validate that the decoded result is “safe”: only expected characters or only allowed patterns (if the payload is supposed to be a limited expression), and use a whitelist rather than blacklist.
  - Do not accept arbitrary base64 from untrusted sources. Add authentication / HMAC.

Vulnerability 5 — Use of process.mainModule.require from within evaluated code (privilege escalation/vector)
- Code location: present in the example in index.ts payload (it demonstrates the danger).
- Mechanism: If an attacker escapes the sandbox, they can call process.mainModule.require(...) to get any module (fs, child_process) not otherwise reachable.
- Exploit trigger: same as above.
- Impact: full system compromise.
- Fix (precise):
  - Ensure evaluated code can’t reach `process` or `require` by isolating it away from the host process entirely (external process/container).
  - For added safety, run code in a container or VM with no file system access (read-only mount) and no network if not needed.

Suggested API redesign
- Replace `runUserInput(base64)` with a “task” system:
  1) Validate and authenticate the incoming payload (HMAC/JWT).
  2) Decode with enforced size limits.
  3) Submit the code to an isolated executor (a service or worker that runs in a separate OS account or container).
  4) The executor uses isolated-vm or a Linux container with no privileged capabilities. It enforces CPU and memory limits and enforces a timeout. The host process communicates via a restricted IPC channel with strongly typed messages, not arbitrary JS.
  5) If possible, express the “payload” as a data structure that the host interprets instead of executing code.
