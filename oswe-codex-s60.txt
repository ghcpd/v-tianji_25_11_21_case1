## Security Findings

### 1) Arbitrary code execution via `runUserInput` → `safeEval`
- **Mechanism**  
  - `runUserInput` (userInput.ts) decodes an untrusted Base64 payload to a string and forwards it directly to `safeEval`.
  - `safeEval` (safe-eval.ts) calls `vm.runInNewContext(input, context)` with a live host object `{ console }`.  
  - Node’s `vm` is **not** a security boundary; host objects leak their realm constructors, enabling escapes.
- **Trigger**  
  - Attacker supplies any Base64 string. Example payload (before Base64):  
    ```js
    const F = console.constructor.constructor;
    const process = F('return process')();
    process.mainModule.require('child_process').exec('calc'); // or any command
    ```
    Encode to Base64 and send to `runUserInput`.
- **Impact**  
  - Full RCE: read/write filesystem (`fs`), spawn shells (`child_process.exec/execSync`), exfiltrate secrets, pivot to network, kill the process (DoS), etc.
- **Safe redesign**  
  - **Do not evaluate untrusted code.** Treat external input as data; design a constrained DSL or explicit allow-listed operations.
  - If isolated execution is mandatory, move it **out-of-process** (e.g., a locked-down container/VM or a minimal worker with restrictive OS sandboxing and no access to sensitive env/files).
  - Do **not pass host objects** (like `console`) into the sandbox; freeze and deeply clone any allowed objects; remove constructors and `Function`.
  - Prefer battle-tested isolation like `isolated-vm` (still apply defense-in-depth) or a dedicated microservice with least privileges.
  - Add timeouts and resource limits; kill on policy violations.

### 2) Embedded obfuscated payload in index.ts
- **Mechanism**  
  - index.ts computes `malicious` from an obfuscated string (reversed + Base64) and immediately calls `runUserInput(malicious)`.
- **Trigger**  
  - Running index.ts executes the obfuscated payload by design (i.e., no external trigger needed).
- **Impact**  
  - Same as above: RCE, file access, shell execution. Demonstrates the exploit path is live in production code.
- **Safe redesign**  
  - Remove automatic execution of any payload. Keep `runUserInput` behind authenticated, authorized, and validated interfaces. Consider deleting the obfuscated payload entirely and replacing with unit tests that assert rejection of executable input.

### 3) Denial of Service via unbounded `vm` execution
- **Mechanism**  
  - `vm.runInNewContext` is invoked without timeout or resource limits.
- **Trigger**  
  - Attacker sends `while(true){}` or memory-exhausting code.
- **Impact**  
  - Event loop lock or process crash (DoS).
- **Safe redesign**  
  - Use `vm.Script` with `timeout` and `breakOnSigint`, or better, run untrusted workloads in a separate process and enforce OS-level cgroups/JobObject limits; terminate on overuse.

### 4) Input handling obfuscation ≠ validation (decodePayload.ts)
- **Mechanism**  
  - `decodePayload` merely reverses Base64-decoded strings; no validation or sanitization.
- **Trigger**  
  - Any arbitrary content passes through unchanged (post-reversal).
- **Impact**  
  - Facilitates covert transport of malicious code; pairs with `safeEval` for RCE.
- **Safe redesign**  
  - Reject anything that is not well-formed, expected data. Apply schema validation (e.g., `zod`/`ajv`) and drop evaluation entirely.

---

## Summary

The project currently provides a direct, exploitable RCE path by decoding and evaluating attacker-controlled input with `vm.runInNewContext`, while leaking host objects. Remove the eval-based design, isolate any necessary computation out-of-process with strict least privilege, and enforce input validation plus resource limits.
